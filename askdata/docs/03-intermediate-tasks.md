# 中级任务攻克方案

> 赛题八要求：初赛 ≥1 个、决赛 ≥3 个中级任务，每个基础分 5 分（质量突出可加分，上限 15 分）
> 本文件给出**推荐顺序、实现方案、可量化指标**，以及已完成部分的实测结果

## 一、任务清单与取舍建议

| 编号 | 任务 | 赛道 | 难度 | 建议 | 理由 |
|---|---|---|---|---|---|
| ① | 要素精准识别与问题改写 | 结构化 | 低 | **做** | 别名词典 + 改写，1~2 天 |
| ② | 可扩展的要素提取 | 结构化 | 中 | 可做 | 与①共用词典，避免 Few-Shot 堆例子 |
| ③ | 智能语义校验与澄清 | 结构化 | 低 | **做** | 规则 + 判断，性价比最高 |
| ④ | 精准表定位 Schema Linking | 结构化 | 中 | **做** | 可量化，答辩有亮点 |
| ⑤ | 高质量多表关联 NL2SQL | 结构化 | 中 | 顺带做 | Demo 已验证多表 JOIN |
| ⑥ | 文档公式识别与计算 | 非结构化 | **高** | **不建议** | 需公式结构解析，工程量陡增 |
| ⑦ | 不标准目录结构鲁棒识别 | 非结构化 | 中高 | 备选 | 需 PDF 层级还原 |
| ⑧ | 文档复杂度评估 | 非结构化 | 中 | 可做加分 | 设计评分规则即可写方法论 |
| ⑨ | 文档质量综合评估 | 非结构化 | **高** | **不建议** | 需 OCR + 图像处理 |

**建议组合：① + ③ + ④**（三个都是结构化赛道，共用同一套基础设施，投入产出比最高）

## 二、任务 ①：要素精准识别与问题改写（推荐先做）

### 问题
用户说"帝都""魔都""销量最好"，而数据库里是 `BillingCity`、`Quantity`。业务术语与规范字段名之间存在鸿沟。

### 方案：别名词典 + 规则改写 + LLM 兜底

三层处理：

```
用户输入
   │
   ├─ 第 1 层：精确匹配别名词典（最快，覆盖高频术语）
   │     帝都 → 北京 / 销量 → 售出数量 / 冠军 → 排名第一
   │
   ├─ 第 2 层：正则归一化（时间、货币、全半角）
   │     "2024年" → 2024 / "1万" → 10000 / "元" → 金额
   │
   └─ 第 3 层：LLM 改写（处理词典未覆盖的新表达）
```

**为什么这样设计（应对中级任务 ②）**：新增业务领域时，只需往词典加条目，
**不需要往提示词里塞示例**，这就是赛题要求的"不依赖 Few-Shot"的可扩展方案。

### 实现要点
- 别名词典存 JSON 文件，支持热加载，方便现场演示"加一条立刻生效"
- 改写后**记录改写痕迹**，前端展示"你的问题被理解为：…"，这本身也是可解释性

### 可量化指标
| 指标 | 目标 | 测量方法 |
|---|---|---|
| 别名识别率 | ≥85% | 构造 20 条含别名的问句，人工标注 |
| 改写后准确率提升 | ≥15 个百分点 | 对比改写前后的 NL2SQL 准确率 |
| 新增领域成本 | 只需加词典条目 | 演示新增 1 个领域，记录改动行数 |

## 三、任务 ③：智能语义校验与澄清（性价比最高）

### 问题
用户问"增长率是多少"却没给时间范围；问"哪个客户最好"却没定义"好"的标准。
系统若不澄清，只能生成错误 SQL。

### 方案：四类缺失检测 + 主动追问

```
提取问题中的"维度槽位"
   │
   ├─ 时间维度缺失？（问增长/同比却没年份）
   ├─ 指标定义模糊？（"最好""最多"未说明按什么排序）
   ├─ 实体指代不明？（"那个客户"指谁）
   └─ 数值范围缺失？（"大额订单"多大算大）
   │
   ├─ 缺失 → 返回澄清话术，不生成 SQL
   └─ 齐全 → 正常走查询
```

**关键设计**：澄清话术要**带选项**，而不是开放式提问。
差：`请补充时间范围。`
好：`您问的是哪一年的增长率？可选 2021–2025。`

### 可量化指标
| 指标 | 目标 | 测量方法 |
|---|---|---|
| 澄清触发准确率 | ≥90% | 15 条模糊问题，是否都触发澄清 |
| 误澄清率 | ≤5% | 15 条明确问题，不应触发澄清 |
| 澄清后完成率 | ≥80% | 用户补充信息后能否正确回答 |

## 四、任务 ④：精准表定位 Schema Linking（答辩亮点）

### 问题
Chinook 有 11 张表，真实业务库常有数十张。
把全部 schema 塞进提示词会导致：提示词过长、模型被干扰项误导、成本上升。

### 方案：两阶段召回 + 候选裁剪

```
第 1 阶段：粗召回（BM25，无 LLM，快）
   对 表名 / 列名 / 取值样本 建索引
   用问题关键词召回候选表
        │
第 2 阶段：精排（LLM 判断）
   把候选表（约 8~14 张）交给模型，输出实际需要的表
        │
第 3 阶段：只把最终表 + 外键路径 放进 SQL 生成的提示词
```

**注意**：`askdata/agent.py` 里的 `_collect_sample_values()` 已经在做"取值样本"的采集，
这是 Schema Linking 第 1 阶段的基础——因为用户问"销售冠军"，字面上没有"Employee"，
但取值样本里有员工名字，靠取值匹配才能召回正确的表。

### 可量化指标
| 指标 | 目标 | 测量方法 |
|---|---|---|
| 召回率（正确表在候选内） | ≥95% | 28 题测试集，人工标注正确表 |
| 候选表数量下降 | 从 11 张降到 ≤8 张 | 统计平均值 |
| 提示词长度下降 | ≥30% | 统计 token 数 |
| 准确率不下降 | ≥基线 | 对比裁剪前后 NL2SQL 准确率 |

## 五、任务 ⑤：高质量多表关联（已部分完成）

Demo 已实测的多表 JOIN：
```sql
-- 3 表关联：员工 ← 客户 ← 发票
SELECT e.FirstName || ' ' || e.LastName AS 销售冠军, SUM(i.Total) AS 销售额
FROM Invoice i
JOIN Customer c ON i.CustomerId = c.CustomerId
JOIN Employee e ON c.SupportRepId = e.EmployeeId
WHERE substr(i.InvoiceDate,1,4) = '2024'
GROUP BY e.EmployeeId ORDER BY 销售额 DESC LIMIT 1;

-- 4 表关联：曲目 ← 专辑 ← 艺人 ← 发票行
SELECT ar.Name, SUM(il.Quantity) AS qty
FROM InvoiceLine il
JOIN Track t  ON t.TrackId = il.TrackId
JOIN Album al ON al.AlbumId = t.AlbumId
JOIN Artist ar ON ar.ArtistId = al.ArtistId
GROUP BY ar.ArtistId ORDER BY qty DESC LIMIT 1;
```

**已实现的鲁棒性机制**：SQL 执行失败时，把数据库报错回灌给模型自我修正，最多 3 次。
