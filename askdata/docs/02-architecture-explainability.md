# 系统架构与可解释性设计

> 对应赛题要求：系统总体架构设计、多源异构数据融合推理策略、可解释性实现方案

## 一、总体架构


## 二、核心模块说明

### 1. 意图路由（agent.plan）

**输入**：用户问题 + 最近 3 轮对话历史
**输出**：`{route, intent, missing, reason}`

路由三分类：
- `db`：纯结构化查询（计数、聚合、排名）
- `kb`：纯文档知识（制度、方法、经验）
- `hybrid`：需跨源（子问题含指标查询 + 文档知识）

**关键设计**：在提示词中明确给出**判定规则 + 反例**。
实测教训：早期版本把"2024年开出多少张发票？同期预计增长多少？"错误路由为 `kb`，
因为模型把整个问题当成"询问报告内容"。加入规则
"问句中只要出现销售额/发票数/客户数/销量这类指标，就必须为 hybrid" 后修正。

**降级策略**：路由 LLM 调用失败时降级为 `kb` 而非直接报错。

### 2. NL2SQL 生成与自我修正（agent._sql_with_repair）

```
生成 SQL
   │
   ▼
SQL 安全校验（db.validate_sql）
   │  只允许单条 SELECT/WITH；拒绝一切写操作、注释、多语句
   ▼
只读执行（mode=ro + pragma query_only）
   │
   ├─ 成功 → 返回结果表
   └─ 失败 → 把「报错信息 + 原 SQL + schema」回灌给模型重新生成
                │
                └─ 最多循环 3 次；仍失败则如实报错，不返回假数据
```

这一机制同时贡献两个评分点：**鲁棒性**（对错误输入的容错）与**准确率**（多一次修正机会）。

### 3. 检索（retrieval.BM25Index）

- **分词**：`jieba` 精确模式，只保留中文词与英文/数字 token
- **算法**：经典 BM25（k1=1.5, b=0.75），`idf = log(1 + (N - df + 0.5)/(df + 0.5))`
- **切片**：按段落合并至 ~420 字符，过长段落按句号切分，带 80 字符重叠
- **可解释**：返回 `(chunk, score, hits)`，**hits 是命中的关键词**，直接展示给用户

**为什么不用向量检索**：BM25 无需模型下载、无 GPU 依赖、毫秒级响应，
且**命中关键词可解释**——用户能看懂"为什么这段被检索到"。
向量检索是后续优化项，不是当前必需项。

### 4. 跨源融合（hybrid 路线，本题最难考察点）

问题示例："2024年销售冠军是谁？请结合知识库总结他的成功方法论。"

```
① 路由判定 hybrid
        │
② SQL：JOIN Employee/Customer/Invoice，按 2024 年分组求和
       → 事实实体：Margaret Park（销售额 197.2）
        │
③ 【关键】用 SQL 查得的字符串事实拼接检索词
       query = 原问题 + "Margaret Park 197.2 ..."
        │
④ BM25 检索 → 命中「03-销售冠军方法论」
        │
⑤ 把「SQL 结果」与「文档片段」一起交给模型
       → 生成融合答案 + 依据标注
```

**第 ③ 步是本方案的核心。** 如果只做两次独立查询再拼接结果，
当知识库中有多个"冠军"（如不同年份、不同口径）时就会答错。
把数据库查到的事实注入检索词，才能**锁定正确的那份文档**。

### 5. SQL 安全（db.py）

| 防护点 | 实现 |
|---|---|
| 禁止写操作 | 正则拒绝 insert/update/delete/drop/alter/create/pragma 等 |
| 禁止多语句 | 语句中不允许出现 `;` |
| 禁止注释绕过 | 拒绝 `--` 与 `/*` |
| 只允许查询 | 必须以 `select` 或 `with` 开头 |
| 数据库层兜底 | `file:...?mode=ro` + `pragma query_only = on` |
| 结果集上限 | `fetchmany(500)`，避免大表撑爆内存 |

## 三、可解释性设计（本题特色得分点）

每次问答**固定产出四类证据**，前端分区展示：

| 证据类型 | 内容 | 前端位置 |
|---|---|---|
| **推理链路** | 每一步的名称 + 具体细节（路由理由、SQL 行数、命中文档） | 左栏有序列表 |
| **SQL 原文** | 最终执行的（已清洗的）SQL 语句 | 右栏代码块 |
| **结果表** | 查询返回的列名与数据行 | 右栏表格 |
| **检索片段** | 文档标题、相关度分数、**命中关键词**、来源段落编号 | 右栏卡片 |

**设计原则**：可解释性不是"事后补一段说明"，而是**在数据流每一环节就地采集**。
例如：
- 路由环节记录 `reason`（为什么选这条路）
- SQL 环节记录 `attempts`（第几次尝试成功）
- 检索环节记录 `hits`（命中了哪些词）与 `score`（相关度）

## 四、多轮对话

- 服务端保留最近 **5 轮**问答（`_history`）
- 路由与 SQL 生成的提示词中注入最近 3 轮，用于**指代消解**
  （如上一轮问了 2024 年，这一轮问"那 2023 年呢"）
- 前端提供 `/api/reset` 清空上下文

**限制**：这是轻量上下文，不是完整会话状态机，未做主题切换检测。

## 五、性能与伸缩性（实测数据）

测试环境：KVM 虚拟机，Python 3.11，实测脚本 `benchmark/run_efficiency.py`，原始数据见 `benchmark/efficiency.json`。

### 1. BM25 检索随文档规模的变化

| 切片数 | 建索引耗时 | 查询平均耗时 | 查询 P95 |
|---:|---:|---:|---:|
| 100 | 858 ms | **0.35 ms** | 0.42 ms |
| 1,000 | 807 ms | **3.16 ms** | 3.78 ms |
| 10,000 | 8.3 s | **40.5 ms** | 50.5 ms |
| 50,000 | 43.6 s | **255 ms** | 283 ms |

> 上表为两次独立运行的一致结果（查询均值偏差 <3%），可复现：`.venv/bin/python benchmark/run_efficiency.py`

**结论**：查询耗时与切片数近似**线性增长**（0.35 → 255 ms，切片数增长 500 倍，耗时增长约 730 倍），
证实当前实现是 **O(N·Q) 全量扫描**，无倒排索引。建索引同样线性增长（且常数较大）。

> **测量说明**：首组（100 切片）的建索引耗时包含 `jieba` 首次加载词典的一次性开销（约 800 ms），
> 不代表真实索引成本，故 100 与 1000 切片的建索引时间相近。查询耗时不受此影响。

**这是当前系统的主要瓶颈。** 在 1 万切片（约 200~400 份长文档）以内可接受（<50 ms）；
超过 5 万切片后检索延迟将超过 SQL 与生成阶段，成为端到端主要开销。

### 2. SQL 执行随表规模的变化

测试语句：`select city, sum(amount) from sales where yr='2020' group by city order by total desc limit 5`（`yr` 上有索引）

| 表行数 | 分组聚合耗时 |
|---:|---:|
| 1,000 | 0.14 ms |
| 10,000 | 0.63 ms |
| 100,000 | 7.51 ms |
| 500,000 | 42.35 ms |

**结论**：在有索引的条件下，SQLite 分组聚合近似线性但常数极小。
50 万行仅需 42 ms，**SQL 不是瓶颈**——这与 BM25 形成鲜明对比。
因此优化重点应放在检索与 LLM 调用，而非数据库。

### 3. 端到端各阶段耗时拆分

| 阶段 | 纯结构化问题 | 纯知识问题 | 说明 |
|---|---:|---:|---|
| 意图路由 | 1,888 ms | 1,718 ms | 一次 LLM 调用 |
| NL2SQL 生成+执行 | 2,050 ms | — | 含生成与执行 |
| 知识库检索 | 0.4 ms | 0.5 ms | **可忽略** |
| 答案生成 | 2,860 ms | 2,071 ms | 一次 LLM 调用 |
| **总计** | **6,799 ms** | **3,789 ms** | |

**结论（关键发现）**：
- **LLM 调用几乎占总耗时的全部**（约 99%：纯结构化 3799/6799 ms 之外几乎无本地开销；
  纯知识问题 3,789 ms 中 LLM 占 3,789 ms）
- BM25 检索在 12 份文档规模下仅 0.4 ms，完全可忽略
- SQL 执行同样是毫秒级

> 注：本表两次运行中，「NL2SQL 生成+执行」阶段**已包含答案生成之外的全部开销**；
> 「生成」为独立的 LLM 合成调用。两阶段均为 LLM 调用，故合计占比接近 100%。

**统计显著性说明**：以上为**单次测量**，虽已做一次预热排除首次加载，
但 LLM 服务延迟本身有波动（实测同一问题不同时刻可在 5~40 秒间变化）。
因此该表**用于说明各阶段占比量级，不宜作为精确基准**。
在真实服务中延迟主要受上游 LLM 负载影响，与本地代码路径关系不大。

**这意味着**：在中小规模知识库场景下，检索和 SQL 都不是性能问题；
系统延迟几乎完全由 LLM 决定。因此**优化优先级**应为：
① 减少 LLM 调用次数（如路由与生成合并）→ ② 缓存高频问题 → ③ 缩短提示词（Schema Linking）。
引入倒排索引只在文档规模上万时才有意义。

> 注：本次每组数据取多次测量的平均值；建索引为一次性开销，服务启动时执行。
