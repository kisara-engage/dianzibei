## 三个创新点

### 创新点 1：事实注入式跨源多跳（解决"拼接式假融合"）

**问题**：多数方案对跨源问题的做法是"查库一次 + 检索一次，把两个结果拼在一起"。
当知识库中存在多个同类实体（如不同年份的销售冠军）时，检索会命中错误文档。

**本方案**：先由 SQL 确定**事实实体**（如 `Margaret Park`），
**把该实体字符串注入检索词**再去文档库检索，从而锁定正确文档。

**实测效果**：问题"2024年销售冠军是谁？请结合知识库总结他的成功方法论"
从修复前的**答案为空**，到修复后正确返回 `Margaret Park` + `三步破冰法`。

### 创新点 2：SQL 自我修正闭环

生成 SQL → 安全校验 → 只读执行 → 失败则把**数据库报错原文回灌**给模型重新生成，
最多 3 次；仍失败则如实报错。这一机制同时提升准确率与鲁棒性。

### 创新点 3：可解释性在数据流中就地采集

不是事后补一段说明，而是在**每个环节就地记录**：
路由环节记 `reason`（为什么选这条路）、SQL 环节记 `attempts`（第几次成功）、
检索环节记 `hits`（命中哪些词）与 `score`（相关度）。
前端分区展示，用户可逐项核对。

## 关键性能发现

**实测结论（反直觉但重要）**：LLM 调用占端到端耗时 **95% 以上**，
而 BM25 检索（12 份文档规模下 0.3 ms）与 SQL 执行（50 万行 42 ms）**都完全不是瓶颈**。

| 规模 | BM25 查询 | SQL 分组聚合 |
|---:|---:|---:|
| 小（100 切片 / 1千行） | 0.34 ms | 0.14 ms |
| 中（1万切片 / 10万行） | 40.8 ms | 7.51 ms |
| 大（5万切片 / 50万行） | 283 ms | 42.35 ms |

**因此优化优先级**：减少 LLM 调用次数 > 缓存 > 缩短提示词 > 倒排索引。

## 工程规范

- **SQL 安全**：只允许单条只读 `SELECT/WITH`，拒绝所有写操作、注释、多语句；
  数据库以 `mode=ro` + `pragma query_only` 打开；有真实测试验证"拒绝后数据确实未被修改"
- **零重型依赖**：检索用纯 Python BM25，无需向量库、无需 GPU、无需下载模型
- **一键启动**：`bash run.sh` 自动建环境、装依赖、自检、启动
